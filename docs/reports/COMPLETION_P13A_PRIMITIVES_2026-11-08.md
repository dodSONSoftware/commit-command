# Completion P13A archive and SQLite primitive checkpoint

Implemented the first P13A building blocks under approved DCP03. This is partial P13A, not a usable product backup/restore workflow or accepted G10.

`app/core/src/backup/archive.rs` provides stored-only format-v1 writing, manifest validation, bounded inspection and bounded component reads. Manifest records format/application/schema versions, timestamp, settings revision, export kind, history/recovery policy and every regular component's path/size/SHA-256. Validated metadata is immutable to callers. Reader/writer stream checksums, reject source drift, duplicate/case/ancestor collisions, unsafe/Unicode paths, extra/missing entries, unsupported schema/compression/encryption, symlink/special types, extra metadata including Unix link fields, truncation and local/central inconsistencies. Parsing performs no extraction or activation. Cancellation is checked during streaming.

Limits: 1 MiB manifest; 10,000 total members including manifest; 256 MiB per content component; 1 GiB content; 1,024 ASCII path bytes and 32 components; bounded 16 MiB central metadata span and 1 GiB plus 32 MiB physical archive. Container names are generated ASCII identifiers; native repository names belong inside typed content rather than archive paths. This deliberate v1 restriction avoids Unicode normalization aliases. The maintained ZIP implementation is exactly pinned to 9.4.2 with default compression/crypto features disabled because preflight uses its unstable streaming entry API. Both local and central metadata are decoded by the library, without a custom ZIP parser. See [pinned ZIP documentation](https://docs.rs/zip/9.4.2/zip/).

`backup::snapshot::database` copies between owner-provided SQLite connections using the SQLite backup API in bounded 64-page steps, cancellation and a 30-second deadline. It refuses nonempty staging databases, caps source/progress/completed size, checks integrity and returns user_version. It never opens arbitrary filesystem paths. WAL regression verifies committed WAL content reaches the target and exact original database/WAL bytes remain unchanged. Target ownership, filesystem durability and cleanup are the caller's responsibility; a failed staging connection must be discarded.

Validation evidence is in `docs/validation/completion-p13a-primitives-2026-11-08/`: 13 focused backup tests; controlled-write library tests; application library tests; strict all-feature/all-target Core Clippy; ordinary host compile with locked dependencies. Application tests require local loopback sockets, so the final run used the approved unsandboxed local fixture execution. Initial sandbox refusal and fixture-construction issues were diagnosed before the final retained results. No live service or user state was used.

Remaining P13A work: private descriptor-relative staging and durable atomic publication; coherent owner-level config/SQLite/settings capture; explicit per-artifact recovery inventory and authority exclusion/sanitization; migration safety integration; disk-space/failure/crash cases and exact catalog boundary coverage. P13B previews/import/restore/automatic backups/retention and native acceptance remain open. No new durable schema or ordinary-write default changed.
