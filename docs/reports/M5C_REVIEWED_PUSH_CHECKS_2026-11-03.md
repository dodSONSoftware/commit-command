# M5C separately reviewed pre-push checks, child gates and interruption history

November 3, 2026. Completed implementation and selected native acceptance checkpoint. GitFleet now offers an independently reviewed **pre-push hook check** bound to an exact non-force source/destination comparison and already-reachable child evidence. Native approval can execute the reviewed hook, with explicit bypass, bounded cancellation and durable unpublished results. No Git push was invoked, no publication transport was implemented, and a completed check grants no push authority. Actual individual/bulk publication authority and uncertain-publication reconciliation remain unfinished.

## Exact review boundary

The Overview planner exposes `Review pre-push check` per explicitly inspected source, with an explicit execute/bypass hook selector. This request is classified as mutating by the native host and remains disabled in the ordinary default build. It uses the existing main-window request → authoritative Rust review → independent native confirmation capability, rather than adding an approval field or executable plan to renderer input. No new Tauri command or origin privilege was added. Main UI selection, a dependency plan, a completed observation and historical results cannot independently approve a hook check.

Core derives the exact source ref/OID, observed destination OID, effective destination/ref, repository/trust/configuration, transport/authentication/tool bindings, child mappings and recent observations. A versioned immutable journal plan also binds the resolved pre-push hook, executable bit/fingerprint, explicit hook policy, both argv values, exact stdin and a digest. The native review displays the stored plan and clearly states that this runs a check without publication. Confirmation is consumed once; decline, replacement and session changes do not restore authority. Source, dependency and transport/hook context are checked again before and after hook execution. Behind/diverged/up-to-date roots and missing outgoing commits refuse this operation.

Pre-push discovery reuses the existing hook inspection code with an explicit name list. Existing commit-hook discovery and trust manifests remain unchanged. The pre-push script itself is shown/bound in the new independent review before execution. Unsupported detected hook managers refuse execute mode; an explicit reviewed bypass is available. This does not broaden the commit engine's hook support.

## Hook behavior and limits

For this supported existing-branch envelope, argv is `[remote name, effective destination]`; stdin is exactly `local-ref SP local-OID SP remote-ref SP observed-remote-OID LF`. The working directory is the non-bare worktree root. Git directory/common directory/worktree/index variables identify the reviewed worktree; inherited Git overrides are removed and recursive Git hooks are disabled. The installed Git hooks manual was inspected and its fingerprint/contract saved. Real fixture scripts independently captured argv, cwd and stdin for SHA-1 and SHA-256.

The hook is trusted unsandboxed code. It can change files or contact servers, and GitFleet does not roll back its effects. Core does not launch a network transport or Git push from this operation. Final source/configuration drift blocks successful completion even when the hook exited successfully. Raw stdout/stderr is bounded and not retained in the journal, error response or IPC; rejection reports a generic hook failure. Hook-passed status is distinct from overall check completion. Nonexecutable or absent hooks are recorded without falsely claiming a hook passed; bypass remains explicit in the reviewed plan and results.

Both proposal and execution have a 60-second overall deadline and cancellation propagation, including subprocess group cleanup through the existing runner. The exact journal record is capped at 2 MiB. Existing dependency bounds remain in force: at most 256 explicit bindings/historical mapping contexts and five-minute observation freshness, checked at return. Limit or context failures do not produce a successful check.

## Child-success gate

A check is for one explicitly selected repository. Every historical child requirement must be **already reachable** on its explicitly chosen recently observed destination branch. Conditional child-first planning and a selected local child source are insufficient. No renderer success flag, completed local commit, prior hook check or old tracking ref can satisfy this gate. A parent is refused until fresh independently approved remote observation plus local ancestry proof establishes the required child commit's availability.

A Git-backed test first refused a pending child's parent, then advanced only the disposable bare child remote by fixture `fetch` and refused again with the old observation. A new independently confirmed observation finally allowed the parent check. This demonstrates the gate without executing a push or claiming that any child publication executor exists. Unselected children remain unselected, and no automatic bulk publication chain was added.

## Durable history and interruption

Versioned `push-check:` records progress through proposed/running to complete, blocked or cancelled. Running is durably recorded before the hook starts. Original-session matching, stored-plan equality and the native one-use capability protect execution. Complete means **the pre-push check completed**, with `published: false`; it does not mean a push happened. The flag describes Core publication only, not a guarantee about arbitrary unsandboxed hook behavior.

Operation results includes pre-push checks in the unified chronology, worktree/kind/result filters and pagination. Orphaned proposed records and running checks project as interrupted after loss of their session/review. The history exposes no retry/resume capability, never reruns hooks, creates no publication operation and removes no foreign lock. An interrupted hook can already have effects: inspect those effects and obtain a fresh review. The recovery test explicitly injected a running phase into a disposable journal and reopened the real application; it is not a claim of actual SIGKILL/crash acceptance. A separate automated test cancelled a proven running real hook and verified cancellation/no replay.

No executor currently enters publication. Ambiguous server outcomes, post-publication observation/reconciliation, expected-old remote transactions, server rejection, and coordinated child-publication success remain separate future work. This checkpoint must not be described as completed push recovery.
