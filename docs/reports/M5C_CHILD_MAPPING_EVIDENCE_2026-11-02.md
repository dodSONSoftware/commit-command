# M5C historical child mapping and observed reachability evidence

November 2, 2026. Historical `.gitmodules` contexts and an explicit child-evidence inspection are implemented. A requirement that persists while its declared URL changes now retains each distinct mapping blob. The desktop lets the operator choose a historical mapping, child repository and previously approved child branch observation. The ancestry check itself is local and contacts no server. No push was implemented or performed; ordinary writes remain disabled.

## Historical mapping contract

Every distinct outgoing tree containing gitlinks is inspected for its root `.gitmodules` entry. Only regular committed blobs are parsed, using Git's bounded `config --blob --null --no-includes`; the working-tree file, includes, child configuration and submodule update commands cannot supply mappings. A path needs exactly one module with one path and one URL. Duplicate/boolean/ambiguous fields, missing or malformed files, nonregular entries and unsupported destinations are surfaced as unusable contexts. Gitlink byte paths and object formats remain intact.

Each path/child-OID requirement retains one context per distinct `.gitmodules` object ID, with an example parent commit for that context. Missing declarations retain an explicit missing context. This preserves destination changes that the previous single-example inventory could not represent. Context identity is the committed blob, not a renderer-provided URL. Raw config and URL credentials are not included in the response. Existing destination classification/redaction is reused; embedded credentials/query/fragment, unsupported mechanisms and malformed URLs cannot become evidence destinations. Oversized URLs are withheld.

The supported matching envelope is explicit absolute HTTPS/SSH URLs and absolute local fixture destinations. Relative URLs and SCP-style shorthand remain unresolved and blocked for evidence: GitFleet does not guess a historical parent base, rewrite a URL or infer a child remote. This is an explicit compatibility limitation. No historical declaration initiates networking or selects an account/profile.

Existing bounds remain: 10,000 comparison commits, 256 distinct outgoing trees, 1,024 unique path/child requirements and 1,024 gitlinks per tree. Added bounds are 8,192 parsed mapping fields per blob, 4,096 mapping contexts, 4,096 bytes per declared URL and 2 MiB of retained path/destination detail. Exceeding inventory/detail bounds refuses the preview rather than returning partial success; oversized/invalid individual declarations stay visible as unusable contexts. Process deadline/cancellation and per-command output limits still apply.

## Explicit observed-branch ancestry evidence

The new scoped `ChildReachability` request names the parent observation, exact parent source OID, raw child path/OID, historical mapping blob, selected child worktree and child observation. Core recomputes the parent preview and resolves the selection against it. It rejects stale/forged source/path/blob/observation selections and unusable mappings.

The child must be a distinct worktree explicitly selected in the active workspace. Its completed, separately approved observation must belong to that worktree and its exact effective destination must equal the selected historical destination. Observations are limited to five minutes old; future timestamps also refuse. Current child repository identity, configuration, transport, authentication/profile, tool and fixture bindings must still match the observation. Branch objects must already be available locally: missing data never triggers fetch. Shallow/grafted histories refuse. The existing isolated reader checks that the required child commit is an ancestor of the actually observed branch OID. A genuine negative ancestry result returns `reachable: false`; a failed/missing/unsupported inspection is an error, never evidence of availability.

Current child transport/trust context and parent preview context are revalidated before returning. The result includes selected identities, mapping, observed child OID/time, generation/configuration and check time. It is ephemeral historical evidence, not a durable grant. A server can change after observation; a five-minute age bound does not make its branch current. Later push review/execution must obtain/revalidate appropriate evidence and handle drift/uncertainty. No tracking ref by itself proves remote availability, no automatic retry occurs and no read result can confirm a push.

## Desktop flow

A successful parent local preview displays all historical mapping contexts and issues. For usable contexts the new form offers explicit choices, initially empty:

1. Choose a historical mapping.
2. Load local child repository choices and select one; the parent itself is excluded.
3. Load previously approved child observations and select one, with exact destination/ref/OID/time shown.
4. Check ancestry locally. The result is labelled reachable/not reachable **from the observed child branch**, with timestamp and no push authority.

Inventory/history loading and the evidence request cannot initiate observation, download, import or credential lookup. The UI instructs the operator to perform a fresh, separate branch observation and separately approved download/import if objects are missing. Changing a selection clears evidence; replacing the parent preview resets the component. Results are never automatically reused as authority. This is available as a local inspection in the ordinary build, while native network/settings/write actions retain their default gate.
