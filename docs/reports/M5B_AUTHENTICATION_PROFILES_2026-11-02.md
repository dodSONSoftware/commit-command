# M5B authentication profiles and settings — November 2, 2026

Implemented the next bounded checkpoint under interview decisions D-040–D-047: named nonsecret authentication profiles, explicitly assigned per worktree/remote through authoritative review and native approval. No push, private-server connection, user credential-store access, global configuration change or ordinary-write default change. This is not full M5B/Gitea/helper compatibility acceptance.

## Delivered behavior

Repository → Remotes and upstream → Authentication profiles and assignments provides profile creation/editing/deletion and explicit assignment/removal after local destination inspection. HTTPS profiles select an absolute helper executable, nonsecret account and optional CA file. SSH profiles select protected known-hosts/public Ed25519 identity files and a private agent socket. No private-key/password/token input or credential management endpoint exists. Fields require exact path text; correction/capitalization/spellcheck are disabled.

Saving or assigning a profile requires the existing one-use authoritative review/native confirmation path. The exact requested change, selected profile, resolved destination/worktree and bound tools are inspectable. Settings writes never execute a credential helper, contact a server, grant worktree trust or authorize a network operation. Renderer requests cannot select the bridge executable: the trusted native host supplies its own executable path. Ordinary read-only builds can inspect profiles but refuse mutation requests, and the native active-write guard blocks conflicting changes.

Versioned nonsecret settings live in the existing state table under `authentication_settings_v1`, without a schema migration or new dependencies. Up to 64 profiles and 1,024 assignments fit within a 1 MiB serialized bound. Names are bounded and case-insensitively unique. Updates use an expected settings revision and one SQLite statement; cancellation, stale revision/tool/destination and declined authority leave the saved catalog unchanged. Assigned profiles must be unassigned before deletion. The native form deliberately starts unassigned and does not infer accounts/agents/helpers or silently apply the first profile.

Assignments bind workspace/worktree identity, exact remote name and resolved fetch URL. A profile binds actual tool/file/agent fingerprints. Preparation and execution re-resolve the destination and validate current profile/tool bindings in Core. Plans carry optional nonsecret profile ID/name/settings revision; legacy records deserialize without it. All profile-bound reviews conservatively become stale when the catalog revision changes. A changed helper/CA/known-host/public identity/agent or application executable requires renewed profile review, including after upgrades. No fallback to another named profile occurs. Existing explicitly supplied host startup policies remain compatible for unassigned remotes; the independent operation review always shows the effective policy.

Network lookup still requires per-worktree trust and separate native operation approval. Removing an assignment invalidates the old review; a new review may deliberately use the current credential-free/startup policy without reviving the removed profile. Observation history is never a credential lookup capability. The existing HTTPS get-only/verified-TLS/Basic/no-redirect and strict SSH selected-agent/known-host/no-fallback envelope remains. Unknown/changed SSH host keys stop execution; users must verify/update known_hosts externally. Helpers remain trusted unsandboxed programs, and their intrinsic store access/side effects are not restricted by forwarding only get.
