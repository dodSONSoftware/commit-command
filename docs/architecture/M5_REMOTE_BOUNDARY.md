# M5 remote inspection and operation boundary

November 2, 2026. This document distinguishes implemented local inspection from the remaining network service. The local development repository must never be pushed by this execution session. Disposable test remotes are the validation boundary for future remote operation code.

## Implemented: local inspection

`remote::inspect` is an application-services Core API. Its only Git commands inspect repository/configuration metadata, validate references, and resolve URLs. Protocol access, lazy fetching and terminal prompts are disabled. It does not invoke remote helpers, credential helpers, SSH commands or servers. A scoped `Remotes` application request is available even for untrusted worktrees; it grants no write/network authority. The per-repository desktop inspector loads only on explicit request and does not fabricate a journaled remote operation.

Host configuration selects the global configuration source. Tests use an isolated empty or explicit global file; the renderer cannot choose a file. Effective configuration includes origin/scope and includes. Remote names remain case-sensitive. Git itself expands `insteadOf` and `pushInsteadOf`, including explicit `pushurl` precedence. All fetch/push URL sets are retained in order; multiple destinations remain visible as ambiguous for mutation. Branch upstream configuration and branch/global push-remote precedence are separate fields. A suggested remote never authorizes or selects a publication destination. These semantics follow [Git remote get-url](https://git-scm.com/docs/git-remote).

Public results contain redacted display URLs, transport classification, configuration origins, refspec counts and policy issues. Raw configuration values/URLs are neither serialized nor persisted. Credentials in user information, query or fragment are hidden; malformed/helper and ambiguous SCP-style destinations are withheld. Credential helper, proxy, SSH command and unsafe TLS configuration are flagged without returning their command strings or secrets. Remote mirror/custom-program settings and absent/ambiguous upstreams are explicit issues. Display content remains inert text and escapes native/control/bidirectional content.

A configuration digest binds the complete effective snapshot without publishing its values. Both local repository generation and effective configuration are checked for drift before returning. The operation is cancellable and bounded by the shared read deadline/output limits, 10,000 config records, 64 remotes, 256 rewrite entries, 32 URLs per set and 1 MiB of expanded URL output. No raw URL is reconstructed from the display projection.

The URL parser is the `url` crate already used by the desktop dependency graph. It is now an optional direct Core dependency under application-services, so untrusted URL parsing does not rely on ad hoc authority/credential parsing. Default Core builds still exclude it and the remote module.

## Next: explicit network service (not implemented by this checkpoint)

1. Keep the read-only adapter's protocol ban. Network requests need distinct typed proposals, durable outcomes and independent native authorization. Trust alone never approves a fetch or push.
2. Resolve exact destination/configuration, source/destination refs, source OID, hook/credential policy and dependency evidence. Bind them to workspace/worktree identities and a short-lived Rust-only review. Raw embedded credentials and ambiguous or unsupported destinations fail closed.
3. Use a separate temporary transport repository under app-owned state so managed repository configuration cannot introduce credential commands, URL rewrites, proxies, upload/receive programs, refspecs, hooks, recursion or lazy network activity after review. Do not simply enable protocols on the inspection or M2 adapter.
4. Start with verified HTTPS and controlled local fixture transport. SSH/credential-helper compatibility remains an explicit implementation/acceptance gate; it is not an agreed exclusion from the product. Preserve certificate/hostname verification and reject unreviewed redirects. External services and actual user credentials are unnecessary for routine tests.
5. Explicitly authorized observation/fetch establishes remote knowledge. Local cached refs must not be presented as a current server observation. Fetch must have explicit bounded ref scope and journal actual local metadata changes. Git supports an empty `--refmap=` to avoid implicit configured mappings and atomic ref updates; [Git fetch documentation](https://git-scm.com/docs/git-fetch) defines those mechanics, but the service still needs its own reviewed publication/recovery contract.
6. Push is a separate exact authorization: non-force update of a specified branch/OID/destination, explicit creation/upstream choices, correct pre-push hook stdin, supported credential handling, and final source/dependency checks. A child commit's availability on the intended reachable remote must be proved before its selected parent is published. No implicit child selection, force push, or push after commit/AI generation.
7. Persist started/completed/failed/uncertain remote phases before side effects. Restart never replays publication. A cancelled/disconnected push with ambiguous publication requires fresh remote observation and review, rather than an automatic retry. Preserve successful prior batch items.
8. Validate isolated local bare and loopback transport fixtures, origin/ref drift, server rejection, auth/transport failures, hooks, cancellation, uncertain outcomes and no implicit upstream/ref changes. Actual supported Keychain/SSH/native behavior requires separate platform evidence.

Inspection alone does not fulfill fetch/push, credential storage, transport authentication, bulk dependency reachability or remote crash recovery. Those requirements remain open in the completion tracker.
